# ADR 004: 双流水线架构

> 状态：已定稿
> 日期：2026-05-26
> [Core] 前台管线 (DSIR→ESIR→FPGA) 归属 Feelings-Core。后台 (编译) 归属 Anim。

---

## 动机

Anim 的交织不是一次性的——Session 运行时需要 1ms 帧级实时响应。但完整的八 Pass 管线不可能在 1ms 内跑完。传统做法是"全部预先编译好，运行时只播放"——但 Anim 不行。Anim 的帧级参数依赖上一帧的生理反馈。不能预编译。必须实时。

两件矛盾的事必须同时成立：全部编译过（安全校验必须完整）。每帧实时跑（响应必须快）。

---

## 决策

双流水线。前台 FPGA 硬实时 + 后台离线预交织。物理隔离。互不抢占。

### 前台实时浅流水线（Session 运行时）

```
帧级循环。每 1ms：

    帧 N  DSIR → ESIR → 固件写入 → 生理采集 → 偏差计算
              ↑                                        │
              └────── 闭环回读到下一帧 DSIR ──────────────┘

这条流水线不走 Pass 0-5。不走 FSIR。不走 PSIR。
FSIR 和 PSIR 在 Session 启动时已完成并缓存。
DSIR 和 ESIR 下沉到 FPGA 门级逻辑执行——不是软件——是硬件。

为什么前台只有 DSIR → ESIR：
    Session 中——用户已经戴着设备。FSIR（感受结构）早就定了。
    PSIR（个人适配）同一 Session 内不变。
    设备组合不变。
    唯一在变的是——上一帧的心率、皮电、呼吸。
    只有 ESIR 需要变。所以前台只跑 ESIR + 偏差修正。

可变流水深度：
    低强度简单包 → 缩减 DSIR 展开深度 → 延迟更低。
    高强度复杂包 → 拆分 DSIR 细分阶段 → 精度更高。

紧急冲刷——硬件衰减状态机，不是硬截断：
    安全预警触发 → 不是"跳到零电平"。是触发固化在 FPGA 门级逻辑里的
    硬件衰减状态机（Hardware Decay Fader）。

    硬件直接接管 DAC 输出控制权（旁路软件写入）。
    在接下来 4-8 个物理帧（4-8ms）内——
    Frame_N   × 0.6
    Frame_N+1 × 0.3
    Frame_N+2 × 0.1
    Frame_N+3 → 保底空包
    固定非线性递减系数。纯硬件乘法器降阶阵列。不依赖软件计算。

    不是硬截断。硬截断 = 岛叶预期链又一次断裂。
    是硬件级温和截断曲线——微秒级响应 + 不给岛叶挨第二锤。
```

### 后台离线预交织流水线（设备空闲时）

```
设备在充电。用户未佩戴。Feelings-Server 后台启动：

    .anim 源码 → Pass 0-2 → Pass 5 → FSIR 缓存到设备本地

下次 Session 启动时：
    直接加载已缓存的 FSIR。
    跳过解析、类型检查、静态安全检查。
    只需要跑 Pass 3 + Pass 6-8。
    Session 启动延迟降至 <100ms。

为什么后台只跑到 FSIR 而不是 PSIR：
    PSIR 需要 PBM。PBM 永不离设备。
    后台在 Server 端跑——不能碰用户数据。
    FSIR 不包含任何个人生理参数。可以安全缓存。
```

## 双流水线全景

```
后台离线（Server 端，设备空闲）             前台实时（设备端，Session 中）
────────────────────────────             ──────────────────────────
Pass 0: LexParse
Pass 1: TypeCheck
Pass 2: StaticSafety
Pass 4: RuntimeGuard                       Session 启动
    （交织期预埋，运行期激活）             → Pass 3: UserStateSafety
Pass 5: FSIRGen                            （用户上下文——只在设备端）
    ↓                                       （用户上下文——只在设备端）
    FSIR 缓存至设备本地                  → 加载缓存 FSIR
                                        → Pass 6: Personalize（PBM 左乘）
                                        → Pass 7: DeviceMap
                                        → Pass 8: CodeGen
                                        → 帧级闭环（1ms/帧，FPGA 硬实时）

后台持续预交织下一个感受包                   前台 Session 独立运行
互不抢占算力                              两套存储空间各自独立
```

---

## 为什么不合并

```
合并方案（单流水线）：
    Session 启动 → 现场跑 Pass 0-8 → 延迟数秒。
    → 第一个 session 被延迟劝退的用户不会再开第二个。

微服务方案（把每个 Pass 拆成独立服务）：
    服务间通信 = 每次序列化/反序列化。
    八 Pass × 每次序列化 = 八次序列化 = 延迟不可控。
    "实时"在这里是 1ms。微服务之间的 RPC 不在这个延迟圈里。

双流水线 = 只有两条线。前台只有两个 IR 层（DSIR + ESIR）。
两条线不通信——前台只读后台写好的 FSIR 缓存。
没有 RPC。没有序列化。文件读写——一次。
```

## 分支预测——帧级感受预判

CPU 靠分支预测器猜下一条指令走哪条路。Anim 用同一套逻辑猜下一帧生理响应往哪个方向偏——不是猜指令，是猜身体。

```
预测器输入    用户历史生理曲线。同一感受包的前几帧偏差方向。
预测对        ESIR 帧零延迟衔接——预测的下一帧已经是下一帧的实际值。
预测错        安全插桩接管——不是 panic。是切回保守帧——不伤用户。

为什么不在 Language 层实现——在 FPGA 层：
    预测器训练数据 = 此人历史上的 HRV 趋势。永不离设备。
    预测器跑在 FPGA 上 = 查寄存器 + 简单线性外推。1ms 内完成。
    放在软件层 = 每次读数据要过 OS 调度 = 延迟不可控。
```

## 为什么双流水线不类比音画同步——控制环不需要对齐。它需要稳定。

视频录制——画面和音频——同一块晶振——PTS 驱动——丢一帧立刻音画不同步。

Anim 的 Pipeline A（离线编译）和 Pipeline B（实时注入）——不共享同一个时钟源。Pipeline A 产出的 ESIR 帧躺在缓存里——Pipeline B 取帧时——不是在读 PTS——是在读人体反馈环。选哪一帧——是分支预测器决定的——不是编译器决定的。

```
音画同步                                   Anim 双流水线
────────                                  ───────────

音轨和画面——同一条时间轴。                      Pipeline A vs Pipeline B——两条不同的时间轴。
                                              编译一次——注入每 1ms。

同步 = 修复 A/V skew——                        不需要同步。
  丢视频帧——或跳音频——                                      
  保持 PTS 对齐。                                    Pipeline B 在每个 1ms tick 里——
                                                       读生理反馈 → 分支预测 → 选帧 → 注入。
丢帧 → 被观众感知。                                       这一帧选错了 → 安全插桩——
                                                       下一帧纠正。
不是"同步"问题——                                    不是"同步"问题——
  是"两个流之间需要保持固定的时间关系"。                        是"控制环能不能稳定"。

控制环不需要对齐。
控制环需要稳定。
```

---

*前台只跑最后两层。后台跑前面五层。两套存储。互不抢占。不是两层跑得比八层快——是 Session 里用户只需要最后两层。前面的已经在设备空闲时跑完了。双流水线不是因为炫技。是因为 1ms 不允许任何多余的东西挡在 DSIR 和 FPGA 之间。一帧不多。一帧不少。而 Pipeline A 和 Pipeline B 之间——不需要音画同步那种对齐——因为控制环不靠 PTS——靠分支预测器在每一帧反馈里自己稳定。*
